# Cautions about fork()

### Cautions about fork()

One more crucial point about threads concerns how they act when the C `fork()` call comes into play. On the majority of systems offering `fork()`, once a process forks, the sole surviving thread is the one that performed the fork. That carries a tangible effect on both how locks must be managed and on every piece of stored state within CPython's runtime.

Because only the "current" thread survives, any locks that other threads were holding will never get released. Python addresses this for [`os.fork()`](https://docs.python.org/3.14/library/os.html#os.fork) by grabbing the locks it relies on internally ahead of the fork and freeing them afterward. It additionally resets every [Lock objects](https://docs.python.org/3.14/library/threading.html#lock-objects) in the child. Where you extend or embed Python, there's no mechanism to notify Python about extra (non-Python) locks that ought to be acquired before, or reset after, a fork. To do the equivalent, you'd have to rely on OS facilities like `pthread_atfork()`. Furthermore, while extending or embedding Python, calling `fork()` outright instead of by way of `os.fork()` (and then returning into, or invoking, Python) can deadlock because one of Python's internal locks is held by a thread now defunct after the fork. [`PyOS_AfterFork_Child()`](https://docs.python.org/3.14/c-api/sys.html#c.PyOS_AfterFork_Child) attempts to reset the required locks, though it can't always succeed.

The disappearance of every other thread likewise means CPython's runtime state there has to be tidied up correctly, which [`os.fork()`](https://docs.python.org/3.14/library/os.html#os.fork) handles. That entails finalizing all the other `PyThreadState` objects that belong to the current interpreter together with all the other [`PyInterpreterState`](https://docs.python.org/3.14/c-api/subinterpreters.html#c.PyInterpreterState) objects. For this reason, plus the distinctive role of the ["main" interpreter](https://docs.python.org/3.14/c-api/subinterpreters.html#sub-interpreter-support), `fork()` ought to be invoked solely in that interpreter's "main" thread — the place where the CPython global runtime was first initialized. The lone exception is when `exec()` follows immediately afterward.
