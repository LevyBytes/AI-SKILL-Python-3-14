# Reference Counts

### Reference Counts

The reference count matters because the computers of today carry a finite (and frequently quite small) amount of memory; it tallies how many separate spots hold a [strong reference](https://docs.python.org/3.14/glossary.html#term-strong-reference) to an object. Such a spot might be a different object, or a global (or static) C variable, or a local variable sitting in some C function. Once the final strong reference to an object is let go (that is, its reference count drops to zero), the object gets freed. Where it holds references to further objects, those references are let go in turn. Those further objects might then be freed as well, provided nothing else references them anymore, and so the cascade continues. (Objects that reference one another clearly pose a difficulty here; the answer, for the time being, is "don't do that.")

You always manipulate reference counts explicitly. The standard route is the [`Py_INCREF()`](https://docs.python.org/3.14/c-api/refcounting.html#c.Py_INCREF) macro for grabbing a fresh reference to an object (that is, bumping its reference count by one), paired with [`Py_DECREF()`](https://docs.python.org/3.14/c-api/refcounting.html#c.Py_DECREF) for letting that reference go (that is, dropping the reference count by one). Compared to the incref one, the `Py_DECREF()` macro carries considerably more complexity, because it has to test whether the reference count has hit zero and, if so, trigger the object's deallocator. That deallocator is a function pointer held in the object's type structure. The type-specific deallocator handles letting go of references to whatever other objects sit inside the object when it's a compound object type, a list for example, plus carrying out whatever extra finalization is called for. The reference count has no opportunity to overflow; the bits set aside for holding the reference count number at least as many as the distinct memory locations across virtual memory (granting `sizeof(Py_ssize_t) >= sizeof(void*)`). Incrementing the reference count is therefore a straightforward operation.

You don't have to keep a [strong reference](https://docs.python.org/3.14/glossary.html#term-strong-reference) (that is, bump the reference count) for each local variable holding a pointer to an object. As a matter of theory, the object's reference count rises by one the moment the variable is set to point at it and falls by one once that variable leaves scope. These two, though, cancel one another out, so by the end the reference count is unchanged. Keeping the reference count around really serves only one purpose: to stop the object from being freed for as long as our variable still points at it. Whenever we already know some other reference to the object exists and outlives our variable by at least as much, there's no call to grab a fresh strong reference (that is, bump the reference count) for the moment. One notable place this comes up is with objects handed as arguments to C functions inside an extension module that Python calls; the calling mechanism promises to keep a reference on each argument throughout the call.

That said, a frequent trap is pulling an object out of a list and clinging to it for a stretch without grabbing a fresh reference. Conceivably some other operation could pull the object from the list, letting that reference go and possibly freeing it. The genuine hazard is that operations that look harmless might run arbitrary Python code that does exactly this; a code path exists allowing control to return to the user out of a [`Py_DECREF()`](https://docs.python.org/3.14/c-api/refcounting.html#c.Py_DECREF), so nearly any operation carries potential danger.

The safe tactic is to lean exclusively on the generic operations (functions whose names open with `PyObject_`, `PyNumber_`, `PySequence_` or `PyMapping_`). These operations invariably mint a fresh [strong reference](https://docs.python.org/3.14/glossary.html#term-strong-reference) (that is, bump the reference count) to whatever object they hand back. That leaves it up to the caller to invoke [`Py_DECREF()`](https://docs.python.org/3.14/c-api/refcounting.html#c.Py_DECREF) once finished with the result; before long this turns into second nature.
