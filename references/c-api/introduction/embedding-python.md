# Embedding Python

### Embedding Python

The single critical job that falls to embedders alone (rather than to extension authors) of the Python interpreter is the initialization, and perhaps the finalization, of the Python interpreter. Nearly all of the interpreter's capability becomes usable only once the interpreter has been initialized.

The fundamental initialization routine is [`Py_Initialize()`](https://docs.python.org/3.14/c-api/interp-lifecycle.html#c.Py_Initialize). It sets up the table of loaded modules and creates the core modules [`builtins`](https://docs.python.org/3.14/library/builtins.html#module-builtins), [`__main__`](https://docs.python.org/3.14/library/__main__.html#module-__main__), and [`sys`](https://docs.python.org/3.14/library/sys.html#module-sys). On top of that, it sets up the module search path (`sys.path`).

[`Py_Initialize()`](https://docs.python.org/3.14/c-api/interp-lifecycle.html#c.Py_Initialize) leaves the "script argument list" (`sys.argv`) unset. When later-running Python code requires this variable, you must assign [`PyConfig.argv`](https://docs.python.org/3.14/c-api/init_config.html#c.PyConfig.argv) and [`PyConfig.parse_argv`](https://docs.python.org/3.14/c-api/init_config.html#c.PyConfig.parse_argv): refer to [Python Initialization Configuration](https://docs.python.org/3.14/c-api/init_config.html#init-config).

Across the majority of platforms (notably Unix and Windows, though the specifics vary somewhat), [`Py_Initialize()`](https://docs.python.org/3.14/c-api/interp-lifecycle.html#c.Py_Initialize) determines the module search path from its best estimate of where the standard Python interpreter executable resides, on the assumption that the Python library sits at a fixed spot relative to that interpreter executable. Specifically, it hunts for a directory called `lib/python*X.Y*` relative to the parent directory in which the executable named `python` turns up along the shell command search path (the environment variable `PATH`).

So if the Python executable is located at `/usr/local/bin/python`, it presumes the libraries reside at `/usr/local/lib/python*X.Y*`. (This very path, in fact, doubles as the "fallback" location, applied whenever no executable file called `python` is discovered along `PATH`.) A user may override this behavior by defining the environment variable [`PYTHONHOME`](https://docs.python.org/3.14/using/cmdline.html#envvar-PYTHONHOME), or prepend extra directories ahead of the standard path by defining [`PYTHONPATH`](https://docs.python.org/3.14/using/cmdline.html#envvar-PYTHONPATH).

An embedding application can guide the search by assigning [`PyConfig.program_name`](https://docs.python.org/3.14/c-api/init_config.html#c.PyConfig.program_name) *before* it calls [`Py_InitializeFromConfig()`](https://docs.python.org/3.14/c-api/interp-lifecycle.html#c.Py_InitializeFromConfig). Keep in mind that [`PYTHONHOME`](https://docs.python.org/3.14/using/cmdline.html#envvar-PYTHONHOME) continues to override this, and [`PYTHONPATH`](https://docs.python.org/3.14/using/cmdline.html#envvar-PYTHONPATH) is still placed ahead of the standard path. Any application demanding complete control must supply its own version of [`Py_GetPath()`](https://docs.python.org/3.14/c-api/interp-lifecycle.html#c.Py_GetPath), [`Py_GetPrefix()`](https://docs.python.org/3.14/c-api/interp-lifecycle.html#c.Py_GetPrefix), [`Py_GetExecPrefix()`](https://docs.python.org/3.14/c-api/interp-lifecycle.html#c.Py_GetExecPrefix), and [`Py_GetProgramFullPath()`](https://docs.python.org/3.14/c-api/interp-lifecycle.html#c.Py_GetProgramFullPath) (every one of them defined in `Modules/getpath.c`).

On occasion you may wish to "uninitialize" Python. The application might, for example, want a clean restart (another call to [`Py_Initialize()`](https://docs.python.org/3.14/c-api/interp-lifecycle.html#c.Py_Initialize)), or it might simply be finished using Python and want to reclaim the memory Python allocated. You can do this by calling [`Py_FinalizeEx()`](https://docs.python.org/3.14/c-api/interp-lifecycle.html#c.Py_FinalizeEx). The function [`Py_IsInitialized()`](https://docs.python.org/3.14/c-api/interp-lifecycle.html#c.Py_IsInitialized) yields true when Python is presently in the initialized state. A later chapter offers further detail on these functions. Observe that `Py_FinalizeEx()` does *not* reclaim every bit of memory the Python interpreter allocated — for instance, memory that extension modules allocated currently cannot be freed.
