# Reference Counts

### 1.10. Reference Counts

In languages such as C or C++, dynamic allocation and freeing of heap memory falls to the programmer. C handles this through the `malloc()` and `free()` functions. C++ uses the `new` and `delete` operators for what is essentially the same purpose, and we'll confine the discussion below to the C case.

Each block of memory obtained via `malloc()` ought eventually to be handed back to the pool of free memory through exactly one matching `free()` call. Timing that `free()` correctly matters. When a block's address slips away without `free()` ever being called on it, the memory it holds stays unusable until the program exits. This goes by the name *memory leak*. Conversely, if a program calls `free()` on a block yet keeps using that block afterward, it collides with the block's reuse by some later `malloc()` call. This goes by the name *using freed memory*. Its ill effects mirror those of referencing uninitialized data — core dumps, wrong results, mysterious crashes.

Unusual code paths are a frequent source of memory leaks. Take, for example, a function that allocates a memory block, performs some computation, and then frees that block again. A later shift in the function's requirements might tack a test onto the computation that spots an error condition and returns from the function early. It's all too easy to overlook freeing the allocated memory block at that early exit, particularly when the exit is bolted on after the fact. Leaks of this kind, once they creep in, frequently slip by unnoticed for ages: the error exit fires in only a tiny share of calls, and most modern machines come with ample virtual memory, so the leak shows itself only in a long-running process that leans on the leaky function repeatedly. For that reason, it pays to head leaks off by adopting a coding convention or strategy that cuts down on errors like these.

Given that Python leans heavily on `malloc()` and `free()`, it too requires a strategy to dodge both memory leaks and the use of freed memory. The approach it settled on goes by *reference counting*. The idea is plain: every object holds a counter, raised whenever a reference to the object gets stored somewhere and lowered whenever a reference to it gets deleted. Once that counter hits zero, the object's final reference has been deleted and the object is freed.

A different approach goes by *automatic garbage collection*. (At times reference counting itself gets labeled a garbage collection strategy too, which is why I say "automatic" to keep the two apart.) Automatic garbage collection's chief upside is that the user never has to call `free()` directly. (A further claimed upside is faster speed or lower memory use — no firm fact, though.) Its downside: for C, no truly portable automatic garbage collector exists, whereas reference counting can be built portably (provided the `malloc()` and `free()` functions are at hand — which the C Standard promises). Perhaps one day C will get a sufficiently portable automatic garbage collector. Until that day, reference counts are what we're stuck with.

Although Python relies on the conventional reference counting implementation, it additionally supplies a cycle detector that operates to catch reference cycles. This lets applications stop fretting about forming direct or indirect circular references; such cycles are the Achilles' heel of garbage collection done with reference counting alone. A reference cycle is made up of objects that carry (perhaps indirect) references back to themselves, so each object within the cycle has a reference count that stays non-zero. Conventional reference counting implementations cannot reclaim the memory of any objects sitting in a reference cycle, nor that of objects referenced from the cycle's objects, even when nothing else points at the cycle at all.

The cycle detector can spot garbage cycles and reclaim them. The [`gc`](https://docs.python.org/3.14/library/gc.html#module-gc) module surfaces a means of running the detector (the [`collect()`](https://docs.python.org/3.14/library/gc.html#gc.collect) function), along with configuration interfaces and the option to switch the detector off while running.
