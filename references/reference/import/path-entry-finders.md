# 5.5.1. Path entry finders

### 5.5.1. Path entry finders

The [path based finder](https://docs.python.org/3.14/glossary.html#term-path-based-finder) bears responsibility for locating and loading Python modules and packages whose place is given by a string [path entry](https://docs.python.org/3.14/glossary.html#term-path-entry). The majority of path entries point to file system locations, though they are not obliged to.

Functioning as a meta path finder, the [path based finder](https://docs.python.org/3.14/glossary.html#term-path-based-finder) realizes the [`find_spec()`](https://docs.python.org/3.14/library/importlib.html#importlib.abc.MetaPathFinder.find_spec) protocol already covered, but it also surfaces extra hooks usable for tailoring how modules get discovered and loaded out of the [import path](https://docs.python.org/3.14/glossary.html#term-import-path).

The [path based finder](https://docs.python.org/3.14/glossary.html#term-path-based-finder) draws on three variables: [`sys.path`](https://docs.python.org/3.14/library/sys.html#sys.path), [`sys.path_hooks`](https://docs.python.org/3.14/library/sys.html#sys.path_hooks) and [`sys.path_importer_cache`](https://docs.python.org/3.14/library/sys.html#sys.path_importer_cache). The `__path__` attributes found on package objects play a part too. These open up further avenues by which the import machinery may be customized.

[`sys.path`](https://docs.python.org/3.14/library/sys.html#sys.path) holds a list of strings that name search locations for modules and packages. Its contents start out from the [`PYTHONPATH`](https://docs.python.org/3.14/using/cmdline.html#envvar-PYTHONPATH) environment variable together with sundry other installation- and implementation-specific defaults. The entries within `sys.path` may name file system directories, zip files, and conceivably other "locations" (consult the [`site`](https://docs.python.org/3.14/library/site.html#module-site) module) worth searching for modules, like URLs or database queries. Nothing but strings belongs on `sys.path`; every other kind of data is disregarded.

Since the [path based finder](https://docs.python.org/3.14/glossary.html#term-path-based-finder) is a [meta path finder](https://docs.python.org/3.14/glossary.html#term-meta-path-finder), the import machinery starts the [import path](https://docs.python.org/3.14/glossary.html#term-import-path) search by invoking the path based finder's [`find_spec()`](https://docs.python.org/3.14/library/importlib.html#importlib.machinery.PathFinder.find_spec) method in the manner described earlier. Whenever a `path` argument is supplied to `find_spec()`, it takes the form of a list of string paths to walk — usually the `__path__` attribute of a package, for an import happening inside that package. A `path` argument of `None` signals a top level import, in which case [`sys.path`](https://docs.python.org/3.14/library/sys.html#sys.path) gets used.

The path based finder steps through each entry on the search path, and for every one it seeks out a fitting [path entry finder](https://docs.python.org/3.14/glossary.html#term-path-entry-finder) ([`PathEntryFinder`](https://docs.python.org/3.14/library/importlib.html#importlib.abc.PathEntryFinder)) for that path entry. Given that this can prove costly (for instance, `stat()` call overheads may attend such a search), the path based finder keeps a cache that maps path entries onto path entry finders. That cache lives in [`sys.path_importer_cache`](https://docs.python.org/3.14/library/sys.html#sys.path_importer_cache) (regardless of its name, this cache really holds finder objects and is not restricted to [importer](https://docs.python.org/3.14/glossary.html#term-importer) objects). By this means the pricey hunt for a given [path entry](https://docs.python.org/3.14/glossary.html#term-path-entry) location's path entry finder happens just one time. User code may freely delete cache entries out of `sys.path_importer_cache`, compelling the path based finder to redo the path entry search.

Where the path entry is missing from the cache, the path based finder loops over every callable found in [`sys.path_hooks`](https://docs.python.org/3.14/library/sys.html#sys.path_hooks). Each [path entry hook](https://docs.python.org/3.14/glossary.html#term-path-entry-hook) within that list receives one argument, the path entry that is to be searched. The callable can either yield a [path entry finder](https://docs.python.org/3.14/glossary.html#term-path-entry-finder) capable of handling the path entry, or it can raise [`ImportError`](https://docs.python.org/3.14/library/exceptions.html#ImportError). The path based finder reads an `ImportError` as a sign that the hook is unable to locate a path entry finder for the [path entry](https://docs.python.org/3.14/glossary.html#term-path-entry) in question. That exception is disregarded and [import path](https://docs.python.org/3.14/glossary.html#term-import-path) iteration carries on. The hook ought to anticipate either a string or a bytes object; how bytes objects are encoded is the hook's call (it could be a file system encoding, UTF-8, or otherwise), and a hook that cannot decode what it received should raise `ImportError`.

Should [`sys.path_hooks`](https://docs.python.org/3.14/library/sys.html#sys.path_hooks) iteration finish without any [path entry finder](https://docs.python.org/3.14/glossary.html#term-path-entry-finder) being produced, then the path based finder's [`find_spec()`](https://docs.python.org/3.14/library/importlib.html#importlib.machinery.PathFinder.find_spec) method records `None` in [`sys.path_importer_cache`](https://docs.python.org/3.14/library/sys.html#sys.path_importer_cache) (marking that no finder exists for this path entry) and gives back `None`, signalling that this [meta path finder](https://docs.python.org/3.14/glossary.html#term-meta-path-finder) was unable to locate the module.

Should one of the [path entry hook](https://docs.python.org/3.14/glossary.html#term-path-entry-hook) callables on [`sys.path_hooks`](https://docs.python.org/3.14/library/sys.html#sys.path_hooks) *return* a [path entry finder](https://docs.python.org/3.14/glossary.html#term-path-entry-finder), then the protocol that follows is applied to request a module spec from that finder, which then serves when the module is loaded.

The current working directory — written as an empty string — gets treated a bit unlike the rest of the entries on [`sys.path`](https://docs.python.org/3.14/library/sys.html#sys.path). To begin with, when the current working directory cannot be worked out or proves not to exist, nothing is stored in [`sys.path_importer_cache`](https://docs.python.org/3.14/library/sys.html#sys.path_importer_cache). Next, the value standing for the current working directory is freshly resolved for every module lookup. Finally, the path placed into `sys.path_importer_cache` and handed back by [`importlib.machinery.PathFinder.find_spec()`](https://docs.python.org/3.14/library/importlib.html#importlib.machinery.PathFinder.find_spec) will be the genuine current working directory in place of the empty string.
