# What's New In Python 3.4 / email — email.compat32-message, email.contentmanager, email.examples, email.generator, email.message, email.policy

### email

[`as_string()`](https://docs.python.org/3.14/library/email.compat32-message.html#email.message.Message.as_string) will now take a *policy* argument that overrides the message's default policy while building its string representation. So `as_string` becomes usable in more situations, sparing you from having to build and run a [`generator`](https://docs.python.org/3.14/library/email.generator.html#module-email.generator) just to feed formatting parameters into its `flatten` method. (Contributed by R. David Murray in [bpo-18600](https://bugs.python.org/issue?@action=redirect&bpo=18600).)

A new method, [`as_bytes()`](https://docs.python.org/3.14/library/email.compat32-message.html#email.message.Message.as_bytes), was added to render a bytes representation of the message much as `as_string` renders a string one. It omits the *maxheaderlen* argument yet does take the *unixfrom* and *policy* arguments. The [`Message`](https://docs.python.org/3.14/library/email.compat32-message.html#email.message.Message) [`__bytes__()`](https://docs.python.org/3.14/library/email.compat32-message.html#email.message.Message.__bytes__) method invokes it, so `bytes(mymsg)` will now yield the obvious outcome: a bytes object holding the fully formatted message. (Contributed by R. David Murray in [bpo-18600](https://bugs.python.org/issue?@action=redirect&bpo=18600).)

The [`Message.set_param()`](https://docs.python.org/3.14/library/email.compat32-message.html#email.message.Message.set_param) message will now take a *replace* keyword argument. Once given, the matching header is refreshed without shifting its spot in the header list. To preserve backward compatibility, the default stays `False`. (Contributed by R. David Murray in [bpo-18891](https://bugs.python.org/issue?@action=redirect&bpo=18891).)

Two new subclasses of [`Message`](https://docs.python.org/3.14/library/email.compat32-message.html#email.message.Message) joined the module ([`EmailMessage`](https://docs.python.org/3.14/library/email.message.html#email.message.EmailMessage) and [`MIMEPart`](https://docs.python.org/3.14/library/email.message.html#email.message.MIMEPart)), alongside a new sub-module, [`contentmanager`](https://docs.python.org/3.14/library/email.contentmanager.html#module-email.contentmanager), plus a new [`policy`](https://docs.python.org/3.14/library/email.policy.html#module-email.policy) attribute [`content_manager`](https://docs.python.org/3.14/library/email.policy.html#email.policy.EmailPolicy.content_manager). For now all documentation sits in the new module, which arrives as part of email's new [provisional API](https://docs.python.org/3.14/glossary.html#term-provisional-API). These classes add a batch of new methods that make pulling content out of and placing content into email messages far simpler. The `contentmanager` documentation and the [email: Examples](https://docs.python.org/3.14/library/email.examples.html#email-examples) cover the specifics. Together these API additions finish off most of the work scoped under the email6 project. The presently provisional API is slated to go final in Python 3.5 (perhaps with a handful of small additions around error handling). (Contributed by R. David Murray in [bpo-18891](https://bugs.python.org/issue?@action=redirect&bpo=18891).)
