# What's New In Python 3.4 / multiprocessing - multiprocessing, runpy

### multiprocessing

Under Unix a pair of fresh [start methods](https://docs.python.org/3.14/library/multiprocessing.html#multiprocessing-start-methods), `spawn` and `forkserver`, are available for launching processes via [`multiprocessing`](https://docs.python.org/3.14/library/multiprocessing.html#module-multiprocessing). They make blending processes with threads sturdier, and the `spawn` method lines up with the behavior multiprocessing has always followed on Windows. The fresh function [`get_all_start_methods()`](https://docs.python.org/3.14/library/multiprocessing.html#multiprocessing.get_all_start_methods) lists every start method the platform offers, [`get_start_method()`](https://docs.python.org/3.14/library/multiprocessing.html#multiprocessing.get_start_method) tells you the active one, and [`set_start_method()`](https://docs.python.org/3.14/library/multiprocessing.html#multiprocessing.set_start_method) selects it. (Contributed by Richard Oudkerk in [bpo-8713](https://bugs.python.org/issue?@action=redirect&bpo=8713).)

[`multiprocessing`](https://docs.python.org/3.14/library/multiprocessing.html#module-multiprocessing) additionally introduces the notion of a `context`, which governs the way child processes get spawned. The fresh function [`get_context()`](https://docs.python.org/3.14/library/multiprocessing.html#multiprocessing.get_context) hands back a context tied to a chosen start method. Its API mirrors the `multiprocessing` module itself, letting you build [`Pool`](https://docs.python.org/3.14/library/multiprocessing.html#multiprocessing.pool.Pool)s and further objects that run inside that context. That lets a framework alongside an application, or separate pieces of one application, share multiprocessing without stepping on each other. (Contributed by Richard Oudkerk in [bpo-18999](https://bugs.python.org/issue?@action=redirect&bpo=18999).)

Aside from the legacy *fork* start method, child processes stop inheriting surplus handles/file descriptors from the parent (part of [bpo-8713](https://bugs.python.org/issue?@action=redirect&bpo=8713)).

[`multiprocessing`](https://docs.python.org/3.14/library/multiprocessing.html#module-multiprocessing) leans on [`runpy`](https://docs.python.org/3.14/library/runpy.html#module-runpy) (the piece that drives the `-m` switch) to set up `__main__` correctly inside child processes whenever the `spawn` or `forkserver` start method is in play. That clears up certain corner cases where mixing multiprocessing, the `-m` command line switch, and explicit relative imports led to puzzling breakage in child processes. (Contributed by Nick Coghlan in [bpo-19946](https://bugs.python.org/issue?@action=redirect&bpo=19946).)
