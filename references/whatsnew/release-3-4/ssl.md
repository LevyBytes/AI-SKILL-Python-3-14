# What's New In Python 3.4 / ssl - ssl

### ssl

[`PROTOCOL_TLSv1_1`](https://docs.python.org/3.14/library/ssl.html#ssl.PROTOCOL_TLSv1_1) and [`PROTOCOL_TLSv1_2`](https://docs.python.org/3.14/library/ssl.html#ssl.PROTOCOL_TLSv1_2) (covering TLSv1.1 and TLSv1.2) are now available; you only get these protocols when Python has been linked against OpenSSL 1.0.1 or a newer release. (Contributed by Michele Orr?? and Antoine Pitrou in [bpo-16692](https://bugs.python.org/issue?@action=redirect&bpo=16692).)

A new helper, [`create_default_context()`](https://docs.python.org/3.14/library/ssl.html#ssl.create_default_context), gives you a standard route to an [`SSLContext`](https://docs.python.org/3.14/library/ssl.html#ssl.SSLContext) configured for a sensible middle ground between interoperability and safety. Those settings are tighter than what the `SSLContext` constructor hands out, and they could be tuned later on, even without advance deprecation, should accepted security guidance shift. Going forward, the suggested approach for any stdlib library that talks SSL is to call `create_default_context()` for an `SSLContext` object, tweak it where necessary, and then hand it off as the *context* argument to the relevant stdlib API. (Contributed by Christian Heimes in [bpo-19689](https://bugs.python.org/issue?@action=redirect&bpo=19689).)

The [`SSLContext`](https://docs.python.org/3.14/library/ssl.html#ssl.SSLContext) method [`load_verify_locations()`](https://docs.python.org/3.14/library/ssl.html#ssl.SSLContext.load_verify_locations) takes a new optional *cadata* argument, by which PEM- or DER-encoded certificates may be supplied straight through strings or bytes, respectively. (Contributed by Christian Heimes in [bpo-18138](https://bugs.python.org/issue?@action=redirect&bpo=18138).)

A new helper, [`get_default_verify_paths()`](https://docs.python.org/3.14/library/ssl.html#ssl.get_default_verify_paths), hands back a named tuple of the paths plus environment variables that [`set_default_verify_paths()`](https://docs.python.org/3.14/library/ssl.html#ssl.SSLContext.set_default_verify_paths) consults when establishing OpenSSL's default `cafile` and `capath`. That can help when you are tracking down default-verification problems. (Contributed by Christian Heimes in [bpo-18143](https://bugs.python.org/issue?@action=redirect&bpo=18143).)

[`SSLContext`](https://docs.python.org/3.14/library/ssl.html#ssl.SSLContext) gained a new method, [`cert_store_stats()`](https://docs.python.org/3.14/library/ssl.html#ssl.SSLContext.cert_store_stats), which tallies how many `X.509` certs, `X.509 CA` certs, and certificate revocation lists (`crl`s) are loaded, along with a [`get_ca_certs()`](https://docs.python.org/3.14/library/ssl.html#ssl.SSLContext.get_ca_certs) method handing back a list of the loaded `CA` certificates. (Contributed by Christian Heimes in [bpo-18147](https://bugs.python.org/issue?@action=redirect&bpo=18147).)

Provided OpenSSL 0.9.8 or newer is present, [`SSLContext`](https://docs.python.org/3.14/library/ssl.html#ssl.SSLContext) carries a new attribute [`verify_flags`](https://docs.python.org/3.14/library/ssl.html#ssl.SSLContext.verify_flags) for steering how certificates get verified — assign it some mix of the new constants [`VERIFY_DEFAULT`](https://docs.python.org/3.14/library/ssl.html#ssl.VERIFY_DEFAULT), [`VERIFY_CRL_CHECK_LEAF`](https://docs.python.org/3.14/library/ssl.html#ssl.VERIFY_CRL_CHECK_LEAF), [`VERIFY_CRL_CHECK_CHAIN`](https://docs.python.org/3.14/library/ssl.html#ssl.VERIFY_CRL_CHECK_CHAIN), or [`VERIFY_X509_STRICT`](https://docs.python.org/3.14/library/ssl.html#ssl.VERIFY_X509_STRICT). Out of the box, OpenSSL performs no CRL verification whatsoever. (Contributed by Christien Heimes in [bpo-8813](https://bugs.python.org/issue?@action=redirect&bpo=8813).)

A new [`SSLContext`](https://docs.python.org/3.14/library/ssl.html#ssl.SSLContext) method, [`load_default_certs()`](https://docs.python.org/3.14/library/ssl.html#ssl.SSLContext.load_default_certs), pulls in a batch of default "certificate authority" (CA) certificates out of default locations that differ by platform. You can use it to bring in both TLS web server authentication certificates (`purpose=`[`SERVER_AUTH`](https://docs.python.org/3.14/library/ssl.html#ssl.Purpose.SERVER_AUTH)) so a client may verify a server, and certificates a server employs while verifying client certificates (`purpose=`[`CLIENT_AUTH`](https://docs.python.org/3.14/library/ssl.html#ssl.Purpose.CLIENT_AUTH)). (Contributed by Christian Heimes in [bpo-19292](https://bugs.python.org/issue?@action=redirect&bpo=19292).)

Two fresh Windows-only functions, [`enum_certificates()`](https://docs.python.org/3.14/library/ssl.html#ssl.enum_certificates) and [`enum_crls()`](https://docs.python.org/3.14/library/ssl.html#ssl.enum_crls), make it possible to pull certificates, certificate details, and CRLs out of the Windows cert store. (Contributed by Christian Heimes in [bpo-17134](https://bugs.python.org/issue?@action=redirect&bpo=17134).)

There is now support for server-side SNI (Server Name Indication) by way of the new [`ssl.SSLContext.set_servername_callback()`](https://docs.python.org/3.14/library/ssl.html#ssl.SSLContext.set_servername_callback) method. (Contributed by Daniel Black in [bpo-8109](https://bugs.python.org/issue?@action=redirect&bpo=8109).)

The dictionary handed back by [`SSLSocket.getpeercert()`](https://docs.python.org/3.14/library/ssl.html#ssl.SSLSocket.getpeercert) carries extra `X509v3` extension entries: `crlDistributionPoints`, `calIssuers`, and `OCSP` URIs. (Contributed by Christian Heimes in [bpo-18379](https://bugs.python.org/issue?@action=redirect&bpo=18379).)
