# What’s New in Python 2.0 / Porting to 2.0 - socket

### Porting to 2.0

Fresh Python releases work hard to stay compatible with the ones before them, and that track record has been quite solid. Even so, certain changes are judged worthwhile enough — usually because they correct early design choices that proved genuinely wrong — that backward compatibility sometimes has to give. The list here covers the Python 2.0 changes that might break existing Python code.

The change most likely to break the largest amount of code is the stricter handling of arguments by certain methods. A few methods accepted several arguments and bundled them into a tuple, notably assorted list methods like [`append()`](https://docs.python.org/3.14/library/stdtypes.html#list.append) and [`insert()`](https://docs.python.org/3.14/library/stdtypes.html#list.insert). Under earlier Python, if `L` is a list, `L.append( 1,2 )` tacks the tuple `(1,2)` onto the list. With Python 2.0 that triggers a [`TypeError`](https://docs.python.org/3.14/library/exceptions.html#TypeError) exception, carrying the message: ‘append requires exactly 1 argument; 2 given’. To fix it, just wrap an additional pair of parentheses around the values so they go in as one tuple: `L.append( (1,2) )`.

Those methods used to be lenient because they leaned on a legacy function in Python’s C interface to read their arguments; 2.0 brings them up to date by switching to [`PyArg_ParseTuple()`](https://docs.python.org/3.14/c-api/arg.html#c.PyArg_ParseTuple), today’s argument-parsing function, which emits clearer error messages and rejects multi-argument calls. Should you absolutely need 2.0 yet be unable to repair your code, you can modify `Objects/listobject.c` and set the preprocessor symbol `NO_STRICT_LIST_APPEND` to keep the old behaviour; doing so isn’t advised.

A handful of functions in the [`socket`](https://docs.python.org/3.14/library/socket.html#module-socket) module stay lenient in the same fashion. As an example, `socket.connect( ('hostname', 25) )` is the proper form, handing over a tuple that stands for an IP address, yet `socket.connect('hostname', 25)` works too. [`socket.connect_ex`](https://docs.python.org/3.14/library/socket.html#socket.socket.connect_ex) and [`socket.bind`](https://docs.python.org/3.14/library/socket.html#socket.socket.bind) are just as relaxed. 2.0alpha1 made these functions strict, but since the documentation itself had shown the wrong multiple-argument form, plenty of people had written code that the tighter checking would break. Facing public pushback, GvR reverted the changes, so for the `socket` module the documentation got corrected and the multiple-argument form is now merely flagged as deprecated; it *will* be made strict again in some later Python version.

In string literals the `\x` escape now consumes exactly 2 hex digits. Formerly it would swallow every hex digit after the ‘x’ and keep the lowest 8 bits of the outcome, making `\x123456` the same as `\x56`.

The [`AttributeError`](https://docs.python.org/3.14/library/exceptions.html#AttributeError) and [`NameError`](https://docs.python.org/3.14/library/exceptions.html#NameError) exceptions carry a friendlier error message, reading roughly `'Spam' instance has no attribute 'eggs'` or `name 'eggs' is not defined`. Formerly the error message held only the absent attribute name `eggs`, so any code that relied on that will break under 2.0.

Some effort went into making integers and long integers somewhat more interchangeable. Back in 1.5.2, large-file support arrived for Solaris so that files over 2 GiB could be read; that change caused the `tell()` method on file objects to give back a long integer rather than an ordinary integer. Certain code subtracted one file offset from another and tried to use the difference to multiply a sequence or slice a string, only to hit a [`TypeError`](https://docs.python.org/3.14/library/exceptions.html#TypeError). With 2.0 you can multiply or slice a sequence using long integers, and it behaves the way intuition suggests; `3L * 'abc'` gives ‘abcabcabc’, and `(0,1,2,3)[2L:4L]` gives (2,3). Long integers are now also valid in many places that formerly took only integers, like the `seek()` method on file objects and the formats the `%` operator handles (`%d`, `%i`, `%x`, etc.). As an illustration, `"%d" % 2L**64` yields the string `18446744073709551616`.

The most subtle long-integer change is that the [`str()`](https://docs.python.org/3.14/library/stdtypes.html#str) of a long integer no longer carries a trailing ‘L’ character, though [`repr()`](https://docs.python.org/3.14/library/functions.html#repr) keeps it. That ‘L’ irritated plenty of people who wished to print long integers indistinguishable from ordinary ones, because they had to take extra steps to trim the character off. That headache is gone in 2.0, but code that does `str(longval)[:-1]` on the assumption the ‘L’ is present will now drop the last digit.

Calling [`repr()`](https://docs.python.org/3.14/library/functions.html#repr) on a float now applies a precision that differs from [`str()`](https://docs.python.org/3.14/library/stdtypes.html#str). `repr()` passes `%.17g` as the format string to C’s `sprintf()`, while `str()` keeps using `%.12g` as it did before. As a result `repr()` can sometimes display additional decimal places relative to `str()` for some values. For instance, since the number 8.1 has no exact binary representation, `repr(8.1)` comes out as `'8.0999999999999996'`, whereas str(8.1) is `'8.1'`.

The `-X` command-line option, which converted every standard exception from a class into a string, is gone; standard exceptions are now always classes. The `exceptions` module that holds the standard exceptions was rewritten from Python into a built-in C module by Barry Warsaw and Fredrik Lundh.
