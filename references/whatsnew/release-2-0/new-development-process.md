# What’s New in Python 2.0 / New Development Process

### New Development Process

Arguably the biggest shift in Python 2.0 isn’t in the code whatsoever, but in the way Python gets built: during May 2000 the Python developers started relying on the facilities offered by SourceForge for keeping source code, following bug reports, and handling the backlog of submitted patches. If you want to file bugs or contribute patches for Python 2.0, reach for the bug tracking and patch manager tools provided on Python’s project page at [https://sourceforge.net/projects/python/](https://sourceforge.net/projects/python/).

Among the services now running on SourceForge, the most crucial is the Python CVS tree, the version-controlled repository that holds Python’s source code. In the past, only about 7 people held write access to the CVS tree, and every patch needed reviewing and committing by someone from that brief roster. Plainly, that approach didn’t scale well. Relocating the CVS tree to SourceForge opened the door to handing write access to additional contributors; by September 2000 some 27 people could commit changes, a fourfold jump. That enables sweeping modifications that nobody would bother attempting if they had to pass through the tiny circle of core developers. As an illustration, one day Peter Schneider-Kamp decided to abandon K&R C compatibility and migrate Python’s C source to ANSI C. Once the python-dev mailing list signed off, he embarked on a burst of checkins spanning roughly a week, fellow developers pitched in to assist, and the work was finished. Had only 5 people held write access, that undertaking would probably have been dismissed as “nice, but not worth the time and effort needed” and never would have happened.

Adopting SourceForge’s services produced a striking acceleration in how quickly development moves. Patches are now submitted, commented on, reworked by contributors other than whoever first wrote them, and passed back and forth among people until the patch is judged ready to commit. Bugs live in a single central spot, can be handed to a particular person to fix, and we’re able to tally the count of open bugs to gauge how we’re doing. None of this was free: developers face more e-mail now, more mailing lists to keep up with, and custom tools had to be created for the new setup. To take one case, SourceForge dispatches default patch and bug notification e-mail messages that are utterly useless, so Ka-Ping Yee built an HTML screen-scraper that produces more helpful messages.

The newfound simplicity of contributing code brought on a few early growing pains, like code getting committed before it was finished or without securing clear sign-off from the developer group. The approval workflow that took shape resembles the one the Apache group uses. Developers may vote +1, +0, -0, or -1 on a patch; +1 and -1 signal acceptance or rejection, whereas +0 and -0 indicate the developer is largely neutral about the change, leaning only slightly toward yes or no. The biggest departure from the Apache model is that the vote is fundamentally advisory, serving to inform Guido van Rossum, who holds Benevolent Dictator For Life status, of where the general sentiment lies. He retains the right to disregard a vote’s outcome, and may approve or reject a change even when the community sees it differently.

Writing the actual patch is the final stage of introducing a new feature, and it’s typically straightforward next to the harder earlier work of devising a sound design. Conversations about new features frequently balloon into sprawling mailing list threads, which makes the discussion tough to track, and nobody can absorb every message sent to python-dev. As a result, a fairly structured procedure was established for composing Python Enhancement Proposals (PEPs), patterned after the internet RFC process. PEPs are draft documents that lay out a proposed new feature, and they’re revised over and over until the community settles on a consensus, whether that means adopting or declining the proposal. To quote the introduction of [**PEP 1**](https://peps.python.org/pep-0001/), “PEP Purpose and Guidelines”:

>

PEP is short for Python Enhancement Proposal. Each PEP is a design document that conveys information to the Python community or sets out a new feature for Python. A PEP ought to supply a concise technical specification of the proposed feature together with the reasoning behind it.

The plan is for PEPs to serve as the chief vehicles for putting forward new features, for gathering the community’s input on a topic, and for recording the design choices made for Python. Whoever authors a PEP bears the duty of forging consensus across the community while also recording the views of those who dissent.

Consult the remainder of [**PEP 1**](https://peps.python.org/pep-0001/) for specifics on the PEP editorial workflow, style, and layout. PEPs reside in the Python CVS tree on SourceForge, even though they aren’t shipped with the Python 2.0 distribution, and they’re also offered in HTML form at [https://peps.python.org/](https://peps.python.org/). By September 2000, 25 PEPs exist, spanning from [**PEP 201**](https://peps.python.org/pep-0201/), “Lockstep Iteration”, through PEP 225, “Elementwise/Objectwise Operators”.
