# What's New In Python 3.0 / Text Vs. Data Instead Of Unicode Vs. 8-bit — codecs, collections.abc, io, os, sys

### Text Vs. Data Instead Of Unicode Vs. 8-bit

Whatever you believed you understood about binary data and Unicode is now different.

- In place of Unicode strings versus 8-bit strings, Python 3.0 works in terms of *text* and (binary) *data*. Every bit of text is Unicode; *encoded* Unicode, however, takes the shape of binary data. Text lives in the [`str`](https://docs.python.org/3.14/library/stdtypes.html#str) type while data lives in the [`bytes`](https://docs.python.org/3.14/library/stdtypes.html#bytes) type. Compared with how 2.x worked, the headline difference is that any try to blend text and data under Python 3.0 throws [`TypeError`](https://docs.python.org/3.14/library/exceptions.html#TypeError); by contrast, blending Unicode and 8-bit strings under Python 2.x succeeded as long as the 8-bit string held only 7-bit (ASCII) bytes, yet handed you [`UnicodeDecodeError`](https://docs.python.org/3.14/library/exceptions.html#UnicodeDecodeError) once non-ASCII values appeared. That value-dependent conduct has produced plenty of frowns down the years.

- Following from this shift in outlook, virtually every piece of code touching Unicode, encodings or binary data will very probably need updating. It's a worthwhile shift, given that the 2.x landscape was riddled with defects rooted in blending encoded and unencoded text. To get ahead of it under Python 2.x, begin reaching for `unicode` across all unencoded text and reserve [`str`](https://docs.python.org/3.14/library/stdtypes.html#str) strictly for binary or encoded data. After that, the `2to3` tool handles the bulk of the labor on your behalf.

- The literals `u"..."` for Unicode text are no longer available to you. The `b"..."` literals, on the other hand, are what you must reach for with binary data.

- Since the [`str`](https://docs.python.org/3.14/library/stdtypes.html#str) and [`bytes`](https://docs.python.org/3.14/library/stdtypes.html#bytes) types can't be blended, conversion between them must always be spelled out. Reach for [`str.encode()`](https://docs.python.org/3.14/library/stdtypes.html#str.encode) when moving from `str` to `bytes`, and [`bytes.decode()`](https://docs.python.org/3.14/library/stdtypes.html#bytes.decode) when moving from `bytes` to `str`. The forms `bytes(s, encoding=...)` and `str(b, encoding=...)` are available too, respectively.

- Just as [`str`](https://docs.python.org/3.14/library/stdtypes.html#str) is, the [`bytes`](https://docs.python.org/3.14/library/stdtypes.html#bytes) type is immutable. A distinct *mutable* type, [`bytearray`](https://docs.python.org/3.14/library/stdtypes.html#bytearray), exists to carry buffered binary data. Practically every API that takes `bytes` takes `bytearray` too. That mutable API rests on [`collections.MutableSequence`](https://docs.python.org/3.14/library/collections.abc.html#collections.abc.MutableSequence).

- Within raw string literals, every backslash is read literally. Consequently the `'\U'` and `'\u'` escapes inside raw strings receive no special handling. As an example, `r'\u20ac'` denotes a 6-character string under Python 3.0, while under 2.6 `ur'\u20ac'` denoted the lone ?euro? character. (Naturally this shift touches raw string literals only; the euro glyph is `'\u20ac'` under Python 3.0.)

- The built-in abstract type `basestring` got removed. Reach for [`str`](https://docs.python.org/3.14/library/stdtypes.html#str) in its place. The `str` and [`bytes`](https://docs.python.org/3.14/library/stdtypes.html#bytes) types share too little behavior to justify a common base class. Every appearance of `basestring` gets swapped for `str` by the `2to3` tool (covered below).

- Files opened in text mode (which remains the default for [`open()`](https://docs.python.org/3.14/library/functions.html#open)) always apply an encoding to translate between in-memory strings and on-disk bytes. Files opened in binary mode (signaled by a `b` in the mode argument) always keep bytes in memory. The upshot is that opening a file with the wrong mode or encoding will more likely make I/O fail noisily rather than quietly yield bad data. A further upshot is that even Unix users must name the right mode (text or binary) when they open a file. A platform-specific default encoding exists, and on Unixy systems it can be configured through the `LANG` environment variable (plus, at times, other platform-specific locale-oriented environment variables). The system default is UTF-8 much of the time, though not always; never lean on that default. Whatever program reads or writes beyond plain ASCII text ought to offer some means of overriding the encoding. The encoding-aware streams in the [`codecs`](https://docs.python.org/3.14/library/codecs.html#module-codecs) module are no longer required for anything.

- To begin with, [`sys.stdin`](https://docs.python.org/3.14/library/sys.html#sys.stdin), [`sys.stdout`](https://docs.python.org/3.14/library/sys.html#sys.stdout) and [`sys.stderr`](https://docs.python.org/3.14/library/sys.html#sys.stderr) hold unicode-only text files (that is, they are instances of [`io.TextIOBase`](https://docs.python.org/3.14/library/io.html#io.TextIOBase)). Should you want to read or write bytes data across these streams, work through their [`io.TextIOBase.buffer`](https://docs.python.org/3.14/library/io.html#io.TextIOBase.buffer) attribute.

- APIs both accept and hand back filenames as (Unicode) strings. That can raise platform-specific headaches, since on certain platforms a filename is an arbitrary byte string. (Conversely, Windows keeps filenames stored natively as Unicode.) By way of a workaround, the bulk of APIs (for example [`open()`](https://docs.python.org/3.14/library/functions.html#open) plus many [`os`](https://docs.python.org/3.14/library/os.html#module-os) module functions) that take filenames will also take [`bytes`](https://docs.python.org/3.14/library/stdtypes.html#bytes) objects in addition to strings, and a handful of APIs offer a means of requesting a `bytes` return value. So [`os.listdir()`](https://docs.python.org/3.14/library/os.html#os.listdir) yields a list of `bytes` instances when its argument is a `bytes` instance, and [`os.getcwdb()`](https://docs.python.org/3.14/library/os.html#os.getcwdb) yields the working directory of the moment as a `bytes` instance. Bear in mind that whenever `os.listdir()` yields a list of strings, any filenames that fail to decode cleanly get skipped instead of triggering [`UnicodeError`](https://docs.python.org/3.14/library/exceptions.html#UnicodeError).

- Certain system APIs such as [`os.environ`](https://docs.python.org/3.14/library/os.html#os.environ) and [`sys.argv`](https://docs.python.org/3.14/library/sys.html#sys.argv) may likewise raise trouble whenever the bytes the system exposes can't be interpreted with the default encoding. The most reliable move is generally to set the `LANG` variable and run the program afresh.

- [**PEP 3138**](https://peps.python.org/pep-3138/): A string's [`repr()`](https://docs.python.org/3.14/library/functions.html#repr) stops escaping non-ASCII characters. It does, however, still escape control characters as well as code points the Unicode standard marks non-printable.

- [**PEP 3120**](https://peps.python.org/pep-3120/): UTF-8 is the default source encoding now.

- [**PEP 3131**](https://peps.python.org/pep-3131/): Identifiers may include non-ASCII letters now. (That said, the standard library stays ASCII-only apart from contributor names found in comments.)

- The `StringIO` and `cStringIO` modules are no more. In their place, import the [`io`](https://docs.python.org/3.14/library/io.html#module-io) module and reach for [`io.StringIO`](https://docs.python.org/3.14/library/io.html#io.StringIO) or [`io.BytesIO`](https://docs.python.org/3.14/library/io.html#io.BytesIO) to handle text and data respectively.

- Have a look as well at the [Unicode HOWTO](https://docs.python.org/3.14/howto/unicode.html#unicode-howto), refreshed for Python 3.0.
