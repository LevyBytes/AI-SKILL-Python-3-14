# Python 3.14.4 final / library / multiprocessing

[gh-144503](https://github.com/python/cpython/issues/144503): Corrects a regression that landed in 3.14.3 and 3.13.12 where the [`multiprocessing`](https://docs.python.org/3.14/library/multiprocessing.html#module-multiprocessing) `forkserver` start method failed with [`BrokenPipeError`](https://docs.python.org/3.14/library/exceptions.html#BrokenPipeError) whenever the parent process owned a very large [`sys.argv`](https://docs.python.org/3.14/library/sys.html#sys.argv). The argv now reaches the forkserver as discrete command-line arguments rather than sitting inside the `-c` command string, which sidesteps the operating system's per-argument length limit.

[gh-146004](https://github.com/python/cpython/issues/146004): Every [`-X`](https://docs.python.org/3.14/using/cmdline.html#cmdoption-X) option supplied on the Python command line now flows through to child processes that [`multiprocessing`](https://docs.python.org/3.14/library/multiprocessing.html#module-multiprocessing) spawns, instead of merely a hard-coded subset. As a result the behavior matches between the default "spawn" and "forkserver" start methods and the older "fork" start method. Options that formerly went unpropagated include: `context_aware_warnings`, `cpu_count`, `disable-remote-debug`, `int_max_str_digits`, `lazy_imports`, `no_debug_ranges`, `pathconfig_warnings`, `perf`, `perf_jit`, `presite`, `pycache_prefix`, `thread_inherit_context`, and `warn_default_encoding`.

[gh-140814](https://github.com/python/cpython/issues/140814): [`multiprocessing.freeze_support()`](https://docs.python.org/3.14/library/multiprocessing.html#multiprocessing.freeze_support) no longer establishes the default start method as a side effect, which formerly made a later [`multiprocessing.set_start_method()`](https://docs.python.org/3.14/library/multiprocessing.html#multiprocessing.set_start_method) call raise [`RuntimeError`](https://docs.python.org/3.14/library/exceptions.html#RuntimeError).

[gh-137335](https://github.com/python/cpython/issues/137335): On Windows, every remaining chance of a named-pipe name collision in [`multiprocessing`](https://docs.python.org/3.14/library/multiprocessing.html#module-multiprocessing) and [`asyncio`](https://docs.python.org/3.14/library/asyncio.html#module-asyncio), however unlikely, has been removed.
