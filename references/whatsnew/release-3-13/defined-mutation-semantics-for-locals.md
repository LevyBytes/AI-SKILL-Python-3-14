# What's New In Python 3.13 / Defined mutation semantics for `locals()` - runpy

> (JIT by Brandt Bucher, inspired by a paper by Haoran Xu and Fredrik Kjolstad. Tier 2 IR by Mark Shannon and Guido van Rossum. Tier 2 optimizer by Ken Jin.)

### Defined mutation semantics for [`locals()`](https://docs.python.org/3.14/library/functions.html#locals)

In the past, what should happen when you mutate the value returned by [`locals()`](https://docs.python.org/3.14/library/functions.html#locals) was left for each Python implementation to decide. Beginning with Python 3.13, [**PEP 667**](https://peps.python.org/pep-0667/) codifies CPython’s historical behavior for the majority of code execution scopes, while it revises [optimized scopes](https://docs.python.org/3.14/glossary.html#term-optimized-scope) (functions, generators, coroutines, comprehensions, and generator expressions) so they expressly return independent snapshots of the local variables currently assigned, taking in locally referenced nonlocal variables captured within closures.

This altered semantics for [`locals()`](https://docs.python.org/3.14/library/functions.html#locals) inside optimized scopes also shapes the default conduct of code execution functions that implicitly aim at `locals()` whenever no explicit namespace is supplied (for example [`exec()`](https://docs.python.org/3.14/library/functions.html#exec) and [`eval()`](https://docs.python.org/3.14/library/functions.html#eval)). Earlier releases left it implementation-dependent whether changes were reachable by calling `locals()` once the code execution function had finished. Within CPython specifically, such code would normally seem to behave as intended, yet it might occasionally break inside optimized scopes because other code (debuggers and execution-tracing tools among them) could reset the shared snapshot in that scope. From now on, the code consistently runs against an independent snapshot of the local variables in optimized scopes, so those changes will never surface in later calls to `locals()`. Reaching the changes made in such cases now demands that an explicit namespace reference be handed to the relevant function. As another route, it may be sensible to revise affected code so it uses a higher level code execution API that hands back the resulting code execution namespace (for instance [`runpy.run_path()`](https://docs.python.org/3.14/library/runpy.html#runpy.run_path) when running Python files from disk).

So that debuggers and similar tooling can dependably update local variables in scopes touched by this change, [`FrameType.f_locals`](https://docs.python.org/3.14/reference/datamodel.html#frame.f_locals) now hands back a write-through proxy onto the frame's local and locally referenced nonlocal variables within those scopes, instead of yielding an inconsistently updated shared `dict` instance whose runtime semantics were undefined.

Refer to [**PEP 667**](https://peps.python.org/pep-0667/) for more, taking in the associated C API changes and deprecations. Porting notes appear below as well for the affected Python APIs and C APIs.
